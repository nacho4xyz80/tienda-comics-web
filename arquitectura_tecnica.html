Análisis Arquitectónico de Tienda Cómics Web

1. Resumen Ejecutivo

El presente documento analiza la arquitectura de software de la aplicación Tienda Cómics Web. El sistema ha sido diseñado de manera "End-to-End" (Tanto en el servidor como en el cliente) bajo los preceptos de la Arquitectura Hexagonal (Ports and Adapters) e Inyección de Dependencias.

Este nivel de agnosticism arquitectónico garantiza una inmensa flexibilidad técnica dividiendo el software cliente y servidor en anillos modulares aislados:

  • Core (Dominio) / UI (Presentación): Reglas de negocio puras en el back-end o renderizado puro del árbol DOM en el front-end, ignorando bases de datos o red.
  • Aplicación (Servicios): Casos de uso neutrales que abstraen el comportamiento transversal. Indiferentes a si la persistencia subyacente es MySQL, LocalStorage, un mock o una API externa.
  • Infraestructura (Adaptadores): Las clases "Driver" que interconectan la aplicación con el ecosistema externo físico (Base de datos, Fetch/APIs de navegador o frameworks HTTP).

3. Justificación de Refactorización Técnica

El Problema Monolítico Tradicional

En sistemas fuertemente acoplados (Spaghetti Code), los controladores o routers realizan múltiples tareas simultáneas: validación HTTP, ejecución de consultas SQL y aplicación de reglas de negocio. Esto conlleva a:

  • Código rígido y propenso a errores ante cambios estructurales.
  • Extrema dificultad para realizar Pruebas Unitarias aisladas sin una base de datos activa.
  • Falta de claridad en las responsabilidades.

El Beneficio Hexagonal

Al refactorizar e introducir Puertos y Adaptadores obtenemos las siguientes garantías técnicas:

  • Alta Modularidad y Bajo Acoplamiento: Los detalles técnicos periféricos pueden reemplazarse. Reemplazar Base de Datos (ej. MySQL por MongoDB) o Framework HTTP (ej. Flask por FastAPI) solo implica reescribir la Infraestructura.
  • Testabilidad Elevada (Inyección de Dependencias): Al depender de Clases Abstractas (core.ports), es trivial enviar repositorios Mock en los Tests Unitarios del Servicio de Aplicación, ignorando por completo la Base de Datos.
  • Encapsulamiento del Dominio: La lógica de negocio fundamental de "Cómo comprar" y "Cómo buscar" es inmutable a los agentes externos.

4. Detalle de Componentes y Responsabilidades

Nota: Esta sección mapea rigurosamente el código actual, destacando los límites lógicos establecidos tanto para el Front-end como para el Back-end.

4.1 Módulos del Front-end (Cliente Hexagonal JS)

Directorio / Archivo Responsabilidad Principal
js/infrastructure/ api.js: Driver genérico (Fetch API) que estandariza las llamadas asíncronas HTTP, lanza las promesas y evalúa cabeceras de respuesta y errores.

storage.js: Abstracción (LocalStorage) para retener persistencias locales desvinculando la lógica real del ecosistema Web Storage API.
js/application/ Servicios de Negocio: (authService.js, cartService.js) Son Casos de Uso. Evalúan las lógicas (ej. calcular coste total agregando cómics) utilizando los "puertos" inyectados externamente, totalmente agnósticos a UI/DOM.
js/ui/domManager.js Capa de Presentación: Funcionalidad 100% aislada para manipular el árbol DOM (usando `innerHTML`, `document.getElementById()`). Nunca hace llamadas directas a un Endpoint de base de datos.
js/main_hexagonal.js Composition Root (Raíz): Es el único archivo que instancia las implementaciones ("wiring"), resolviendo la Inyección de Dependencias e instanciando el servicio. Luego asocia los EventListeners del usuario disparando métodos del Dominio.

4.2 Módulos del Back-end (Servidor FastAPI)

Directorio Componentes Clave y Rol
core/ Entidades (entities.py): DTOs puramente descriptivos usando Pydantic (Comic, Usuario).
Puertos (ports.py): Contratos formales usando abc.ABCMeta (ComicRepository, CompraRepository).
application/ Servicios de Casos de Uso (compra_service.py, comic_service.py): Evalúan reglas de negocio (ej. "Lanzar error si el carrito está vacío al finalizar la compra"). Dirigen el tráfico de datos entre el Cliente y el Repositorio de base de datos.
infrastructure/ Adaptadores de Base de Datos (mysql_adapters.py): Ejecutan queries SQL con DB-API 2.0 y mapean el RowSet a Entidades.
Rutas API (api_routes.py): Conecta HTTP (FastAPI) al servicio, atrapa Excepciones y las formatea como Códigos HTTP 4xx/5xx limpios e Inyecta las Dependencias (Depends).
